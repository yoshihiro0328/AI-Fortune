# Plusローカル入口の拒否：原因と接続修正

## 原因

停止試行1466ec22の終了記録と、同じ `startRuntime` / `server.mjs` を資格情報なしで起動した再現を照合した。
修正前の `GET /subscription-test/c` は、CookieなしのHTTP要求では303だったが、実際に接続済みのアプリ内ブラウザーとChromeではサーバーが403を返した。操作ツールの表示は `ERR_BLOCKED_BY_CLIENT` だった。

入口はCookie文字列に `sb-` が含まれるだけで拒否していた。localhostのCookieはポートを跨ぐため、別のローカル利用で残っていた認証Cookieも今回のログインとして扱っていた。ホスト検査後のHTTP記録で403が確認でき、要求がサーバーへ到達しなかったという仮説は否定できた。修正後の両ブラウザーでは、値を記録しない診断で `foreignAuthIgnored=true`、`currentAuthRejected=false` を確認した。

以前の独立したブラウザーコンテキストによる合成試験には、既存Cookieがなかったため検出できなかった。過去のCookie値・JWT・秘密値は取得・再掲していない。

## 修正とレビュー

- ローカル試験の起動ごとに独立したランダムCookie名前空間を生成。プロキシ資格情報からは導出しない。
- Next/Supabaseに渡すCookieと、ブラウザーに返すCookieを今回の名前空間に限定。既存Cookieは削除せず、今回の認証へ取り込まない。
- 今回の認証Cookieがある状態で入口からC/Dを切り替える拒否は維持。認証Cookieの分割、削除属性、重複・想定外の名前を検証。
- 診断にはパス・HTTPステータス・真偽値だけを記録し、Cookie値を含めない。
- 資格情報なしの `browser-preflight.mjs` を追加。同じランチャー・アプリ画面・通信制御を使い、外部サービスへの接続部分だけローカル固定応答とする。
- 既存の継続試験に、同じプロジェクトの古いCookieとログイン後の入口拒否を追加。

差分を自己レビューし、アプリ本体の認証・RLS・ユーザー情報を変更していないこと、既存Cookieを消さないこと、Host検査・Webhook転送トークン・OS通信制御を維持することを確認した。ブラウザー拡張や保護機能の無効化は行っていない。
